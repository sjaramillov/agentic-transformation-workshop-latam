2026-10-16 · Python 3.11+ · 1179 LOC · Portfolio: ccs-mit-analysis-20261016

Executive Summary

This report evaluates whether the original MIT booking service is safe to be called by write-enabled AI agents that create, read and cancel their own bookings. It examines eight dimensions: API & Tooling, Authentication & Authorization, State & Memory, Human-in-the-Loop, Data Access, Discovery & Documentation, Observability and Engineering Practices. It is a design-time architecture review of controls present in code and configuration, not a penetration test or runtime scan, and no application code was modified.

Detailed Findings

HighAUTH-Q4: Identity Propagation and Delegation
Section: AUTH · Authentication & Authorization
FINDING
The system carries exactly one identity dimension. booking_lab/auth.py issues tokens whose only subject claim is sub (agent-a/agent-b in the fixtures) with no act, azp or on-behalf-of claim, and booking_lab/service.py treats the verified sub as the sole principal. Internal hops do not propagate it: payment() and deliver() authenticate to the payment provider and audit sink with the static shared bearer tokens PAYMENT_TOKEN and AUDIT_WRITE_TOKEN, so the payment provider authorizes any holder of the token and performs no per-principal check (charges has no principal column in booking_lab/schema.sql). There is no token exchange, no OAuth on-behalf-of flow, and no audit field distinguishing agent-as-self from agent-acting-for-a-user: booking_lab/audit.py FIELDS records principal only.
GAP
An agent acting for a specific human cannot be bounded by that human's permissions, and the audit ledger cannot show which end user a booking was made for. Any component holding PAYMENT_TOKEN can charge or refund any operation_id regardless of which principal owns it.
RECOMMENDATION
Add a delegation claim (for example act.sub or an explicit obo subject) to the token contract, persist both the actor and the subject on operations/outbox/audit events, and have the payment provider verify the booking principal alongside its service token.
Effort: Medium (1-2 months)

HighAUTH-Q5: Credential Management
Section: AUTH · Authentication & Authorization
FINDING
No secret is hardcoded anywhere in the source: booking_lab/run.py generates every credential per run with secrets.token_hex (JWT key, five PostgreSQL role passwords, PAYMENT_TOKEN, AUDIT_SIGNING_KEY, AUDIT_WRITE_TOKEN, AUDIT_READ_TOKEN), writes them to 0600 env files under .local/ which .gitignore excludes (.local/, .env*), and docker() deliberately never prints container environments. Minimum key strength is enforced at startup (service.py refuses a JWT_KEY shorter than 32 characters; audit.py initialize() refuses audit secrets shorter than 32). There is, however, no secrets-manager integration (no aws_secretsmanager_* or Vault reference exists - no IaC files are present) and no rotation path: all secrets are process-lifetime environment variables, and the JWT key is a single symmetric secret shared between the token issuer fixture (booking_lab/auth.py encode) and the verifying API, so any API host can mint tokens for any principal.
GAP
Rotation requires restarting every container, and compromise of an API host or its env file yields the ability to forge any agent identity. There is no managed rotation, no asymmetric verification key and no audit of secret access.
RECOMMENDATION
Move JWT verification to an asymmetric key pair (private key held only by the issuer, API verifying against a published JWKS) and source all runtime secrets from AWS Secrets Manager or Vault with scheduled rotation before any externally exposed deployment.
Effort: Medium (1-2 months)

HighAUTH-Q7: Agent Identity Suspension
Section: AUTH · Authentication & Authorization
FINDING
There is no mechanism to revoke one agent identity. booking_lab/auth.py verify performs stateless signature and claim validation with no jti, no denylist lookup and no principal allowlist; booking_lab/service.py accepts any sub matching [a-zA-Z0-9_-]{1,64} that is signed with the shared JWT_KEY. Because the key is shared by all principals, the only revocation action available is rotating JWT_KEY and restarting the API, which invalidates every agent at once. No API-key table, account-disable endpoint or external identity store exists - searched the repository for revocation endpoints and IaC, none present.
GAP
A misbehaving or compromised agent cannot be isolated without a platform-wide outage for all agents.
RECOMMENDATION
Introduce a per-principal status check in the authorization path (a principals table consulted by Handler.dispatch, or an external IdP supporting per-client disablement) so a single sub can be suspended without rotating the shared key.
Effort: Medium (1-2 months)

HighSTATE-Q4: Circuit Breakers and Resilience
Section: STATE · State & Memory
FINDING
Timeouts and durable retries are implemented, but there is no circuit breaker and no backoff. booking_lab/service.py sets connect_timeout=3, statement_timeout=10000 and lock_timeout=8000 on every PostgreSQL connection, urlopen timeout=4 on both the payment provider and the audit sink, and an 8 s socket timeout per request; failures are converted to a retryable 503 rather than a hang. Retry is durable but unthrottled: main() in worker mode loops recover() + deliver() every 250 ms unconditionally, and recover() re-drives up to 100 pending operations each pass, so a provider that is down or slow is re-called four times a second indefinitely with no breaker, no exponential backoff and no per-operation attempt ceiling. No resilience library is present (booking_lab/requirements.txt contains only psycopg[binary]==3.3.6).
GAP
A dependency outage produces a sustained retry storm from the worker (amplified by each 4 s timeout held open), and there is no fast-fail state to stop the API from queuing more work against a known-bad provider.
RECOMMENDATION
Add exponential backoff with jitter and an attempt or age ceiling to the worker loop, and a circuit breaker around payment() and the audit POST that short-circuits to the existing retryable 503 while open.
Effort: Medium (1-2 months)

HighSTATE-Q5: Rate Limiting and Throttling
Section: STATE · State & Memory
FINDING
No rate limiting or throttling exists anywhere on the agent-facing surface. booking_lab/service.py serves the API from ThreadingHTTPServer with no limiter, no per-principal counter and no concurrency cap; searched the repository for API-gateway/WAF throttling (no IaC files of any kind exist), rate-limiting middleware and X-RateLimit/Retry-After headers - none found. The only protections are per-request bounds: an 8 KiB body cap, an 8 s connection timeout, and the per-container cgroup limits booking_lab/run.py applies to the lab (--memory 256m --cpus 1 --pids-limit 128), which shed load by exhaustion rather than by a documented limit.
GAP
A runaway agent loop can saturate the API replicas, the PostgreSQL connection pool and the synthetic payment provider at machine speed; a thread is spawned per connection with no ceiling.
RECOMMENDATION
Enforce per-principal request-rate and concurrency limits in front of the API (an API Gateway usage plan, a reverse proxy, or middleware keyed on the verified sub) and return 429 with Retry-After so agents can self-throttle.
Effort: Medium (1-2 months)

HighSTATE-Q6: Blast Radius and Transaction Limits
Section: STATE · State & Memory
FINDING
Only per-request value bounds exist; there are no per-principal business limits. booking_lab/service.py validates a single booking amount as an int in 1..10000000 and booking_lab/schema.sql enforces amount > 0, which caps one transaction but not aggregate exposure. Nothing limits bookings per principal per hour, cumulative synthetic spend per session, or cancellations and refunds per principal: cancel() has no counter, and the only LIMIT 100 clauses are internal worker batch sizes in recover() and deliver(), not caller-facing caps. There are no bulk endpoints, so blast radius grows by repetition rather than by a single large call.
GAP
A correct-but-runaway agent can create or cancel an unbounded number of bookings and drive an unbounded number of synthetic captures and refunds; the maximum business impact of an agent error is undefined.
RECOMMENDATION
Add configurable per-principal limits enforced in the write path (bookings per interval, cumulative amount per session, cancellations per interval) keyed on the verified sub, returning a distinct terminal error code when exceeded.
Effort: Medium (1-2 months)

HighHITL-Q1: Draft/Pending State
Section: HITL · Human-in-the-Loop
FINDING
There is no reviewable pre-commit state. booking_lab/service.py create() inserts the operation with status NEW and immediately calls advance(), which charges the payment provider and commits the CONFIRMED booking within the same request; the operations status values in booking_lab/schema.sql (NEW, CHARGED, CONFIRMED, COMPENSATING, COMPENSATED, DECLINED, CANCELLING, CANCELLED) are saga progress markers, not approval states - NEW is already a committed intent to charge, and the worker will drive it to CONFIRMED without any human action. bookings.status allows only CONFIRMED or CANCELLED. There is no draft, PENDING_REVIEW or proposed record and no create-then-confirm two-step API.
GAP
An agent cannot propose a booking for human review; every accepted POST captures a payment and confirms a booking autonomously.
RECOMMENDATION
Add a proposed/pending status to operations and bookings plus a separate confirm endpoint requiring a distinct scope, so an agent-initiated booking is materialised only after review. The existing saga and idempotency machinery can carry the extra state without redesign.
Effort: High (2-4 months)

HighHITL-Q2: Configurable Approval Gates
Section: HITL · Human-in-the-Loop
FINDING
No approval gate exists or can be configured. booking_lab/service.py authorizes a request on token scope alone and then executes it; there is no approval endpoint, no per-operation flag, no amount threshold that diverts to review, and no external workflow integration. The only operator-facing control in the repository is the faults table, which booking_lab/schema.sql documents as test-administrator-only with no HTTP endpoint, and LAB_FAULTS=1 is set only for the lab API containers in booking_lab/run.py.
GAP
High-risk operations (large synthetic amounts, cancellation of a confirmed booking) cannot be made to require a human decision at the application layer.
RECOMMENDATION
Introduce a configurable policy check in Handler.dispatch (for example amount above a threshold, or DELETE on a CONFIRMED booking) that parks the operation in a pending-approval state and exposes an approve/reject endpoint gated by a distinct scope.

MediumDATA-Q3: Selective Query Support
Section: DATA · Data Access
FINDING
The collection endpoint is unbounded. booking_lab/service.py answers GET /bookings with SELECT id,itinerary,amount,status FROM bookings WHERE principal=%s ORDER BY id and returns every row in a single {"bookings":[...]} body; there is no limit, offset, cursor, status filter or sort parameter, and the path regex accepts only /bookings or /bookings/{64-hex}, so no query string is interpreted at all. Single-item retrieval is implemented by fetching the full principal-scoped set and filtering it in Python, so the database read grows with the principal history even for a one-record lookup.
GAP
An agent with a long booking history receives an unbounded array that can exhaust its context window, and the service cannot express "most recent N" or "CONFIRMED only".
RECOMMENDATION
Add limit/cursor pagination plus a status filter to GET /bookings with a server-side default and maximum page size, and push the single-id lookup into SQL (WHERE principal=%s AND id=%s) instead of filtering in the handler.
Effort: Low (2-4 weeks)

MediumDATA-Q4: Input Validation and Schema Enforcement
Section: DATA · Data Access
FINDING
Validation is strict but rejections are opaque. booking_lab/service.py enforces Content-Type application/json, a 1..8192 byte body, a JSON object, an exact field set {itinerary, amount}, amount of Python type int in 1..10000000, itinerary matching [A-Z]{3}-[A-Z]{3}, Idempotency-Key matching [A-Za-z0-9_-]{1,100}, a parseable UUID X-Correlation-ID and a path matching /bookings/[a-f0-9]{64}; all database access is parameterised through psycopg and CHECK constraints back the enum and amount rules (booking_lab/schema.sql). Every one of those failures raises a bare ValueError that the single handler converts to the same response: 400 {"error":"invalid_request"} with no field name, no constraint and no accepted format. The payment provider likewise raises ValueError on a bad operation_id or amount.
GAP
An agent that constructs a malformed payload cannot tell which field was rejected or why, so it must guess across several candidate fixes - the blind-retry loop the rubric warns about.
RECOMMENDATION
Return a structured validation body (for example {"error":"invalid_request","fields":[{"field":"itinerary","constraint":"pattern","expected":"[A-Z]{3}-[A-Z]{3}"}]}) by raising a typed validation error carrying the field and constraint, instead of a bare ValueError.
Effort: Low (2-4 weeks)

MediumDATA-Q5: Temporal Metadata and Freshness
Section: DATA · Data Access
FINDING
Temporal metadata is partial and is not exposed to callers. booking_lab/schema.sql defines created_at timestamptz NOT NULL DEFAULT clock_timestamp() on outbox and created_at timestamptz NOT NULL on audit_events, and the signed ledger records carry created_at plus a retain_until deadline (booking_lab/audit.py), so the audit path is timestamped in timezone-aware form. The business tables have no temporal columns at all: operations, bookings and charges carry no created_at or updated_at, and the API responses from booking_lab/service.py return only id, itinerary, amount, status - no timestamp, no X-Data-Age, no consistency indicator. Reads are strongly consistent (direct PostgreSQL reads with Cache-Control: no-store), so freshness is implicitly current, but nothing states it.
GAP
An agent cannot tell when a booking was created or last changed, cannot order its own history by time, and cannot assert freshness from the response itself.
RECOMMENDATION
Add created_at/updated_at timestamptz columns to operations, bookings and charges and surface them (UTC, ISO-8601) in the booking responses; optionally emit an explicit consistency marker since reads are strongly consistent.
Effort: Medium (1-2 months)

MediumOBS-Q1: Distributed Tracing and Structured Logging
Section: OBS · Observability
FINDING
Correlation is carried through the data path but not through logs, and there is no tracing. booking_lab/service.py accepts X-Correlation-ID (or generates a UUID4), validates it as a UUID, stores it on operations, stamps every outbox event with it, attributes a cancellation to its own request correlation, and propagates it into the signed audit ledger (booking_lab/audit.py FIELDS includes correlation_id); booking_lab/run.py asserts the principal and correlation id reach the outbox for booking.confirmed. Logging, by contrast, is deliberately minimal and unstructured: Handler.log_message is a no-op and the only emitted lines are plain strings 'request_retry_pending <ExceptionTypeName>', 'worker_retry_pending' and 'recovery_pending' with no JSON envelope, no correlation_id, no principal and no operation id. No OpenTelemetry or X-Ray instrumentation exists and traceparent is neither read nor forwarded on the outbound payment and audit calls (booking_lab/requirements.txt contains only psycopg[binary]==3.3.6).
GAP
A failed agent-initiated request cannot be reconstructed from logs: the retry line cannot be tied to a principal, operation or correlation id, and there is no span linking the API, payment provider and audit sink.
RECOMMENDATION
Emit JSON log lines including correlation_id, principal, operation_id, route and outcome (continuing to exclude tokens and bodies), and add OpenTelemetry instrumentation that reads and forwards traceparent across the payment and audit calls.

MediumENG-Q3: Rollback Capability
Section: ENG · Engineering Practices
FINDING
No deployment or rollback mechanism is defined. There is no blue/green or canary configuration, no CodeDeploy or Helm release, no traffic shifting and no feature flag in the repository; booking_lab/run.py starts containers directly with docker run and its finish() deliberately retains containers and volumes for review rather than managing a release lifecycle. MediumENG-Q5: Encryption at Rest for Agent-Accessible Data
Section: ENG · Engineering Practices
FINDING
There is no encryption at rest. PostgreSQL data lives in a plain Docker volume created by booking_lab/run.py (docker volume create {prefix}-db-data) and the signed audit ledger in a second plain volume holding /audit/ledger.sqlite; neither is encrypted. No KMS key, kms_key_id, LUKS/dm-crypt setting, PostgreSQL TDE extension or SQLite encryption provider appears anywhere (no IaC files exist; booking_lab/requirements.txt lists only psycopg[binary]==3.3.6). Confidentiality rests on filesystem permissions and process isolation instead: booking_lab/audit.py chmods the ledger to 0600 and the volume is chowned to uid 65532 with mode 0700, env files are 0600, containers run read-only, non-root and cap-drop ALL, and the pg_dump produced during the e2e is written 0600. Transport is also unencrypted (plain HTTP and non-TLS libpq on Docker networks, mitigated today by the --internal network and 127.0.0.1-only publication). The data at rest is synthetic and non-PII.
GAP
A host-level compromise or a copied volume exposes the full booking and synthetic charge history and the audit ledger in cleartext; the ledger HMAC gives tamper evidence but no confidentiality.
RECOMMENDATION
Place both volumes on encrypted storage with a managed key (KMS-backed EBS/EFS or an encrypted RDS instance, plus an encrypted archive for the ledger), and enable TLS for libpq and for the payment and audit HTTP hops before any externally exposed deployment.
Effort: Medium (1-2 months)

LowDATA-Q1: Sensitive Data Classification
Section: DATA · Data Access
FINDING
Stage A = Yes: the system persists principal-scoped business data and synthetic financial transactions (booking_lab/schema.sql operations, bookings, charges, outbox, audit_events).
