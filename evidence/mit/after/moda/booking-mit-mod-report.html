Executive Summary

🟠 Significant Modernization Required (Remediation Required) — Overall score 1.99 / 4.0 · rule matched: 2-11 High → Remediation Required

Repository Status. A containerized Python booking service with PostgreSQL, a synthetic HTTP payment provider, a recovery/audit worker and an independent signed audit ledger. The application layer is unusually strong on correctness — durable saga, transactional outbox, identity-scoped idempotency, per-role database privileges and an 18-case integration suite with crash, outage and tamper scenarios. The deployment and operations layers are effectively absent.

Key Findings. 5 High, 19 Medium and 11 Low findings. The High findings are a self-managed database, no CI/CD, no encryption at rest, no deployment strategy and local-filesystem-only retention of audit artifacts.

Remediation Plan. Two pathways are triggered: Move to Modern DevOps (pipeline plus declarative IaC) and Move to Managed Databases (RDS for PostgreSQL plus an immutable object archive for the ledger). Neither decomposition nor containerization is warranted — boundaries already exist and images already exist.

Recommended Actions.

  • INF-Q11 CI/CD Automation: Add one pipeline that builds the image, runs run.py e2e against disposable Docker resources, records the evidence JSON as a build artifact and publishes the image digest to Amazon ECR. This converts the existing suite into an enforced quality gate and unblocks every other modernization action.
  • INF-Q2 Managed Databases: Move the application database to Amazon RDS for PostgreSQL with Multi-AZ (the schema uses only standard PostgreSQL constructs, so the move is homogeneous) and pair the signed SQLite ledger with an S3 Object Lock archive for its records and checkpoints.
  • DATA-Q1 Unstructured Data Storage: Add an S3 bucket with Object Lock in compliance mode for audit snapshots and checkpoints, with versioning, a lifecycle policy matching the 90-day minimum and a KMS key, and write checkpoints from the pipeline so they are retained outside the sink's administrative boundary as AUDIT.md requires.

SEC-Q2: Encryption at Rest HIGH

Category: Security Baseline · Priority: P1 · Effort: Medium · Phase: 1 · Score: 1 (Not Ready)

FINDING

Two at-rest surfaces exist and neither is encrypted. The PostgreSQL data volume is a plain Docker volume with no encryption configuration (booking_lab/run.py) and the authoritative audit ledger is an unencrypted SQLite file whose only protection is POSIX mode 0600 and ownership by uid 65532 (booking_lab/audit.py initialize(); run.py chowns /audit to 65532 mode 0700). Generated secret files, pg_dump output and audit snapshots are likewise plaintext at mode 0600. No KMS key or kms_key_id appears anywhere.

RECOMMENDATION

Encrypt both surfaces with customer-managed KMS keys: storage_encrypted with a CMK on the RDS instance, SSE-KMS on the S3 audit archive, encrypted EBS/EFS if the sink keeps local state. Define a documented rotation policy and hold the ledger signing key in AWS KMS or Secrets Manager rather than an environment variable.

Evidence: booking_lab/audit.py

INF-Q4: Async Messaging and Streaming MEDIUM

Category: Infrastructure, Platform, and DevOps · Priority: P2 · Effort: Medium · Phase: 2 · Score: 2 (Needs Work) · archetype-calibrated

FINDING

Event propagation uses a transactional outbox in PostgreSQL: emit() inserts into outbox in the state-change transaction, and deliver() claims rows FOR UPDATE SKIP LOCKED, posts to the independent audit sink over HTTP, writes the projection, then stamps delivered_at. Redelivery is idempotent by event UUID. No managed broker (SQS, SNS, EventBridge, MSK, Kinesis) and no self-managed Kafka/RabbitMQ exist; the queue is a DB table polled every 250 ms.

RECOMMENDATION

SEC-Q3: API Authentication LOW

Category: Security Baseline · Priority: P2 · Effort: Low · Phase: 3 · Score: 3 (Partial)

FINDING

Every business endpoint requires a per-request bearer token with a method-mapped scope (GET → bookings:read, POST → bookings:write, DELETE → bookings:cancel). booking_lab/auth.py validates the HMAC signature with compare_digest, pins the header to exactly HS256/JWT, checks issuer, audience, exp/nbf/iat, caps lifetime at 300 s, rejects non-finite and boolean NumericDate values, constrains sub by regex and returns 403 on scope mismatch. All reads are filtered to the authenticated principal, and the E2E asserts 401 for ten malformed/forged token variants, 403 for insufficient scope and 404 for cross-principal access. The payment provider and audit sink each require their own bearer token with constant-time comparison; only health endpoints are unauthenticated, intentionally.

RECOMMENDATION

For an operated deployment, replace the symmetric lab issuer with an external authorization server issuing asymmetrically signed tokens (RS256/ES256) validated against a cached JWKS, keep the existing scope and principal-isolation checks exactly as they are, and add gateway throttling per client.

Evidence: booking_lab/auth.py

OPS-Q7: Incident Response Automation LOW

Category: Operations & Observability · Priority: P2 · Effort: Medium · Phase: 3 · Score: 3 (Partial)

FINDING

A defined class of incidents is self-healing without human intervention: the worker loop runs recover() and deliver() every 250 ms, re-driving every operation left in NEW, CHARGED, COMPENSATING or CANCELLING under an advisory lock and draining undelivered outbox rows with UUID deduplication. The E2E proves recovery from a refund outage, an API crash after an external commit, a provider outage, a crash after refund and an audit-delivery privilege failure. Procedural documentation exists for the audit path (booking_lab/AUDIT.md) with an executable offline verifier (booking_lab/audit_verify.py).

RECOMMENDATION

Keep the recovery worker as the primary self-healing mechanism and add structured runbooks (SSM Automation documents) for the incidents it cannot resolve, each linked to the alarm that detects it. Convert the AUDIT.md verification procedure into a scheduled automated check so ledger integrity is confirmed continuously.
