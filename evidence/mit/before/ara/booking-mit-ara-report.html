Executive Summary

This report evaluates whether the booking service is safe to be called by autonomous agents, across eight dimensions: API & Tooling, Authentication & Authorization, State & Memory, Human-in-the-Loop, Data Access, Discovery & Documentation, Observability and Engineering Practices. The repository is a write-bearing stateful-CRUD application (Python standard-library HTTP API, durable saga with a transactional outbox, synthetic payment provider and a recovery/audit worker over PostgreSQL) assessed at write-enabled agent scope: agents create, read and cancel their own bookings.

Transactional integrity is strong and backed by executable tests — identity-scoped idempotency, saga compensation with refund, cross-replica advisory locking and durable attributed audit events all pass. The gating defect is that the audit trail, while attributed and durable, is not immutable or tamper-evident. Remaining safety work concentrates on identity lifecycle and blast-radius containment; quality work concentrates on a published versioned contract, observability and deployment maturity. The current runtime binds API ports to localhost; an externally exposed deployment would additionally require the rate limiting, IaC, encryption-at-rest and alerting gaps below to be closed.

AUTH-Q3: Action-Level Authorization

High
Section: AUTH · Dimension: Authentication & Authorization · Native: RISK-SAFETY · Priority: P1

FINDING

Authorization is scope-based: dispatch() requires bookings:read for GET and bookings:write for every mutating method (service.py lines 211-217), and verify() rejects a token whose scope claim lacks the required value with 403 (auth.py lines 43-45). run.py proves a bookings:read token cannot create a booking. But POST /bookings and DELETE /bookings/{id} share the single bookings:write scope, so a create-only agent identity cannot be expressed — any identity able to book is also able to cancel and trigger a refund.

GAP

No action-level separation within the write surface: there is no bookings:cancel (or delete-specific) scope, and no per-method permission matrix, so read/write is the only granularity available.

RECOMMENDATION

Split the write scope into bookings:create and bookings:cancel (or add a per-method required-scope map in dispatch()) so an agent can be granted booking creation without cancellation/refund authority.

AUTH-Q4: Identity Propagation and Delegation

High
Section: AUTH · Dimension: Authentication & Authorization · Native: RISK-SAFETY · Priority: P2

FINDING

The token carries a single sub claim that becomes the principal and is used for both authorization and data scoping (auth.py lines 39-46, service.py lines 218-234). There is no delegation dimension: no act/on-behalf-of claim, no token exchange, and no way to distinguish an agent acting as itself from an agent acting for a named human user. Downstream propagation is absent as well — payment() authenticates to the provider with a single static shared bearer token (PAYMENT_TOKEN) and forwards only operation_id and amount, so the provider cannot attribute a charge to the calling principal, and X-Correlation-ID is not forwarded either (service.py lines 36-50).

GAP

No identity propagation or delegation model: one flat principal, no subject/actor separation, and a shared service credential on the only outbound call, so neither the payment provider nor its audit trail can see which principal caused a charge.

RECOMMENDATION

Add an actor/subject distinction to the token (e.g. sub = end user, act.sub = agent) enforced in verify(), and propagate principal plus X-Correlation-ID to the payment provider so charges are attributable end to end.

Effort: Medium (60–90 days)

AUTH-Q5: Credential Management

High
Section: AUTH · Dimension: Authentication & Authorization · Native: RISK-SAFETY · Priority: P2

FINDING

No credentials are hardcoded: DATABASE_URL, AUDIT_DATABASE_URL, PAYMENT_TOKEN and JWT_KEY are all read from the environment (service.py lines 20-22, 36-42, 215) and run.py generates per-run random secrets into mode-0600 env files and never prints container environments (run.py lines 37-45, 24-29, 86-90). .gitignore excludes .env*. What is missing is any managed secret: there is no Secrets Manager/Vault/SSM reference anywhere in the repository, no rotation path, and the JWT secret is symmetric HS256 shared between issuer and verifier (auth.py lines 20-26, 30-34), so any component holding JWT_KEY can mint a token for any principal, including agent identities it does not own. There is also no key id/rotation overlap, so rotating JWT_KEY invalidates all live agent tokens at once.

GAP

Secrets are environment-injected with no managed store, no rotation and no separation between signing and verification authority; the symmetric JWT key is a forge-any-principal credential held by the API process itself.

RECOMMENDATION

Store JWT_KEY, PAYMENT_TOKEN and the database URLs in a managed secret store with rotation, and move token issuance to asymmetric signing (RS256/ES256 with kid + JWKS) so the API only holds verification material and keys can be rotated with overlap.

AUTH-Q6: Immutable Audit Logging

High
Section: AUTH · Dimension: Authentication & Authorization · Native: BLOCKER · Priority: P1

FINDING

Every write is attributed: operations, outbox and audit_events all persist principal and correlation_id (schema.sql lines 2-24), events are written in the same local transaction as the state change via emit() and drained to a separate audit sink by deliver() (service.py lines 28-31, 158-170). Runtime roles are append-only on the sink: audit_writer holds only INSERT plus SELECT(id), and booking_app has no access at all (schema.sql lines 40-46); run.py asserts that no runtime role can DELETE or UPDATE audit_events (run.py, rights case). However nothing in the repository makes the trail tamper-evident: there is no hash chaining or signature over audit_events rows, no WORM/object-lock or log-file-validation equivalent, no retention policy, and no IaC configuring an independent immutable store. AUDIT_DATABASE_URL in run.py points at the same PostgreSQL instance as the application database, so the bootstrap owner (postgres) can rewrite history undetected.

GAP

Attribution and durability are implemented and tested, but immutability/tamper-evidence is not: audit_events is an ordinary table in the same database, protected only by GRANTs that a superuser or a compromised bootstrap role can revoke, with no cryptographic integrity and no retention control.

RECOMMENDATION

Move the audit sink out of the application database into an append-only store (e.g. a separate account/instance with object-lock or CloudTrail-style log file validation), add a per-principal hash chain or signature over (operation_id, principal, correlation_id, event_type, created_at) written by deliver(), and define a retention policy. Keep the existing outbox so delivery remains durable.

Effort: Medium (60–90 days)

AUTH-Q7: Agent Identity Suspension

High
Section: AUTH · Dimension: Authentication & Authorization · Native: RISK-SAFETY · Priority: P1

FINDING

There is no revocation surface. verify() accepts any correctly signed, unexpired token and consults no denylist, no jti and no principal status (auth.py lines 28-46); there is no admin endpoint, no key-per-principal, and no principal table. The only containment is the 300-second exp (auth.py line 16) and rotating the shared JWT_KEY, which invalidates every agent identity simultaneously and therefore cannot isolate one misbehaving agent.

GAP

No per-identity suspension or revocation mechanism: a compromised agent token remains valid until expiry, and the only kill switch (rotating the shared symmetric key) is platform-wide.

RECOMMENDATION

Add a principal registry with an enabled flag checked in verify(), include a jti in issued tokens, and expose a revocation path (denylist or per-principal key) so a single agent identity can be disabled without affecting others.

STATE-Q4: Circuit Breakers and Resilience

High
Section: STATE · Dimension: State & Memory · Native: RISK-SAFETY · Priority: P1

FINDING

Timeouts are set everywhere: psycopg connect_timeout=3 with statement_timeout=10s and lock_timeout=8s (service.py lines 20-22), urlopen(timeout=4) on the payment call, and connection.settimeout(8) per request (service.py lines 43, 196). Failures fail closed - OSError/HTTPError are converted to a retryable 503 with retry_same_idempotency_key (service.py lines 44-50, 246-248) and the operation stays in a resumable state so the worker finishes it (recover(), service.py lines 146-156). What is absent is any circuit breaker or backoff: the worker loop re-drives up to 100 pending operations every 250 ms unconditionally (service.py lines 275-283), so a sustained payment-provider or audit-sink outage produces a tight unbounded retry against the failing dependency with no half-open state, no jitter and no shedding.

GAP

No circuit breaker and no exponential backoff on the payment provider or audit sink; retries are a fixed 250 ms hot loop, so a dependency outage is amplified rather than damped.

RECOMMENDATION

Add exponential backoff with jitter and an attempt counter per operation in recover()/deliver(), plus a circuit breaker around payment() that fast-fails to 503 while open.

Effort: Medium (60–90 days)

High
Section: STATE · Dimension: State & Memory · Native: RISK-SAFETY · Priority: P1

FINDING

No rate limiting exists at any layer. The API is a bare ThreadingHTTPServer bound in-process (service.py lines 288-291) with no throttling middleware, no connection or concurrency cap, no per-principal request budget, and no gateway in front of it - the repository contains no IaC, no API Gateway usage plan and no WAF configuration (searched for *.tf, *.cfn.*, template.yaml, docker-compose*, k8s manifests and rate-limit middleware in requirements.txt: none present). run.py binds the API to 127.0.0.1 only (run.py line 89), which limits exposure in the lab but is not a rate control. STATE-Q6: Blast Radius and Transaction Limits

High
Section: STATE · Dimension: State & Memory · Native: RISK-SAFETY · Priority: P2

FINDING

There is one business cap: a single booking amount must be an int in (0, 10000000] (service.py lines 221-226) and the schema enforces amount > 0 on bookings and charges (schema.sql lines 10-12, 25-28). There are no per-principal or per-session limits - nothing caps bookings per principal per hour, cumulative captured amount per principal, or cancellations/refunds per session, and there is no bulk endpoint or configurable limit table. An agent holding a valid bookings:write token can create unlimited distinct bookings (each with a fresh Idempotency-Key) and refund them, each one a real captured charge against the provider, with no business-domain ceiling.

GAP

No configurable per-caller business transaction limits: only a per-request amount ceiling exists, so cumulative agent blast radius (total spend, booking count, refund count per principal) is unbounded.

RECOMMENDATION

Add a per-principal limits table (max bookings/hour, max cumulative amount/session, max cancellations/hour) checked inside create() and cancel() before the saga advances, and reject over-limit requests with a distinct terminal error code.

Effort: Medium (60–90 days)

HITL-Q1: Draft/Pending State

High
Section: HITL · Dimension: Human-in-the-Loop · Native: RISK-SAFETY · Priority: P1

FINDING

The operations table has a rich status machine (NEW, CHARGED, CONFIRMED, COMPENSATING, COMPENSATED, DECLINED, CANCELLING, CANCELLED - schema.sql lines 2-7), but every state is a saga step, not an approval point: advance() drives NEW straight through charge to CONFIRMED within the same request (service.py lines 64-86) and create() calls advance() immediately after inserting the operation (service.py lines 113-130). There is no DRAFT/PENDING_REVIEW status, no create-then-confirm two-step API, and no approval endpoint, so an agent-initiated booking captures payment and is confirmed with no reviewable intermediate state.

GAP

No draft or pending-approval state that an agent can write to before a human commits; the first durable effect of POST /bookings is an external payment capture.

RECOMMENDATION

Add a PENDING_APPROVAL status and an opt-in two-step flow (POST /bookings creates the operation without calling payment(); a separate confirm action advances the saga) so agent-proposed bookings can be reviewed before any charge.

DATA-Q3: Selective Query Support

Medium
Section: DATA · Dimension: Data Access · Native: RISK-QUALITY · Priority: P2

FINDING

GET /bookings returns every booking belonging to the principal with no bounds: the query is SELECT id,itinerary,amount,status FROM bookings WHERE principal=%s ORDER BY id with no LIMIT, and no limit/offset/cursor/filter/sort parameter is parsed anywhere (service.py lines 235-242). Single-item retrieval is implemented by fetching the whole list and filtering it in Python (service.py lines 238-240), so per-item reads also scale with the principal's total booking count. Column projection is explicit and narrow, which is good, but result-set size is unbounded.

GAP

No pagination, filtering or sorting on the list endpoint, and per-id reads fan out over the full result set, so an agent with many bookings receives an unbounded response that can exhaust its context window.

RECOMMENDATION

Add limit (default and maximum) plus a cursor or offset and a status filter to GET /bookings, push the id predicate into SQL for the single-item route, and return the applied limit in the response envelope.

DATA-Q4: Input Validation and Schema Enforcement

Medium
Section: DATA · Dimension: Data Access · Native: RISK-QUALITY · Priority: P2

FINDING

Validation at the boundary is strict and systematic: body() rejects non-JSON content types, empty bodies and bodies over 8192 bytes and requires a JSON object (service.py lines 184-191); the booking payload must match exactly {itinerary, amount} with amount a Python int in (0, 10000000] and itinerary matching [A-Z]{3}-[A-Z]{3} (service.py lines 221-226); Idempotency-Key must match [A-Za-z0-9_-]{1,100}; the path is matched against /bookings/[a-f0-9]{64}; X-Correlation-ID must parse as a UUID; all SQL uses psycopg parameter binding. The weakness is the rejection signal: every validation failure collapses into a single generic 400 {"error":"invalid_request"} (service.py lines 244-245) with no field name, no constraint and no accepted format, so an agent cannot tell which field it got wrong.

GAP

Validation errors are unstructured and undifferentiated - one opaque 400 for malformed JSON, a bad itinerary, an out-of-range amount, a bad idempotency key and a bad correlation id alike - forcing agents into blind retry loops.

RECOMMENDATION

Return field-level validation errors, e.g. {"error":"invalid_request","errors":[{"field":"itinerary","constraint":"pattern","expected":"AAA-BBB"}]}, while keeping the current whitelist semantics and 8 KiB body cap.

Medium
