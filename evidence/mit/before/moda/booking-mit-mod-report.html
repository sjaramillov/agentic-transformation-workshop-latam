INF-Q2: Managed Databases: PostgreSQL self-managed in a container with no failover HIGH

Category: Infrastructure, Platform, and DevOps · Score 1 (Not Ready) · P1 · Effort Medium · Phase 1 · Evidence: booking_lab/images.lock.json
FINDING
The sole datastore is a self-managed PostgreSQL container: booking_lab/images.lock.json pins postgres@sha256:721873c3..., started by booking_lab/run.py with a generated POSTGRES_PASSWORD on a local Docker volume. No managed database resource (aws_rds_*, aws_dynamodb_*, aws_docdb_*, aws_elasticache_*) exists. One instance, no replica, no failover. The audit sink is the same instance under the audit_writer role, so the audit trail shares a failure domain with the data it audits. Every durability guarantee the service provides - persisted saga state, transactional outbox, append-only audit trail - rests on a single unmanaged, unreplicated PostgreSQL process with no automated patching, failover or managed backup.
RECOMMENDATION
Migrate to Amazon RDS for PostgreSQL (or Aurora PostgreSQL) with multi_az=true, storage_encrypted=true on a customer-managed KMS key and backup_retention_period >= 7. Validate pg_advisory_lock, pg_advisory_xact_lock and FOR UPDATE SKIP LOCKED on the target before cutover - session-scoped advisory locks are incompatible with transaction-mode pooling, so re-run the eight-concurrent-request case through any proxy. Place the audit sink in a separate database or account.

SEC-Q2: Encryption at Rest: No encryption at rest on any data surface HIGH

Category: Security Baseline · Score 1 (Not Ready) · P1 · Effort Low · Phase 1 · Evidence: booking_lab/run.py
FINDING
No encryption at rest is configured. The PostgreSQL data directory is a plain Docker volume mounted at /var/lib/postgresql/data with no volume or filesystem encryption and no aws_kms_key or kms_key_id anywhere. The pg_dump output from dump_restore() is written in cleartext to {work}/workshop.sql, and the per-container .env files written by Lab.env hold the four role passwords, the symmetric JWT_KEY and PAYMENT_TOKEN in cleartext on disk. Filesystem permissions are the only control (work dir mode 0700, dump and .env files 0600). Payment-adjacent records (principals, itineraries, amounts, charge states, refund counts) and the immutable audit trail sit unencrypted at rest, as do live credentials and the JWT signing key. Permissions-only protection does not survive volume snapshot, host compromise, disk disposal or backup copy, and provides no key rotation or access audit trail.
RECOMMENDATION
On the managed database set storage_encrypted=true with a customer-managed KMS key and ensure snapshots inherit it. Move the four role passwords, JWT_KEY and PAYMENT_TOKEN into Secrets Manager so plaintext never reaches disk; inject at task start rather than via --env-file. Encrypt any dump before it leaves the host and write it to an S3 bucket with SSE-KMS and a lifecycle policy. Document a key rotation policy. Keep the existing 0700/0600 discipline as defence in depth, not as the control.

INF-Q3: Workflow Orchestration: Durable saga hand-coded with no orchestration service MEDIUM

Category: Infrastructure, Platform, and DevOps · Score 2 (Needs Work) · P2 · Effort Medium · Phase 2 · archetype-calibrated · Evidence: booking_lab/service.py
FINDING
Archetype-calibrated (stateful-crud). The multi-step booking workflow is a structured, resumable state machine in application code: booking_lab/schema.sql constrains operations.status via CHECK to eight states and booking_lab/service.py::advance() transitions from persisted state, with transition() and result() committing each change together with its outbox event. No aws_sfn_*, Temporal, Camunda or MWAA is used. Retry policy, backoff, timeout escalation and workflow visibility are implicit in the code path and the worker's fixed 0.25s poll loop. There is no execution history, no per-step timeout, and no operator-visible view of in-flight or stuck operations.
RECOMMENDATION
Keep the saga in application code - it is durable and correct, and moving it to Step Functions would break the single-transaction commit of operations+bookings+outbox that the compensation tests verify. Close the visibility gap instead: alarm on the count of operations in ('NEW','CHARGED','COMPENSATING','CANCELLING') older than a threshold (the query already exists as the pending_operations invariant), and add a bounded attempt counter with backoff.

INF-Q4: Async Messaging and Streaming: Transactional outbox on PostgreSQL rather than managed messaging MEDIUM

Category: Infrastructure, Platform, and DevOps · Score 2 (Needs Work) · P2 · Effort Medium · Phase 2 · archetype-calibrated · Evidence: booking_lab/schema.sql
FINDING
Archetype-calibrated (stateful-crud). Async delivery exists and is well built but self-managed: booking_lab/schema.sql defines an outbox table, emit() inserts in the same transaction as the state change, and deliver() drains with FOR UPDATE SKIP LOCKED and inserts into audit_events with ON CONFLICT(id) DO NOTHING. No aws_sqs_*, aws_sns_*, aws_eventbridge_*, aws_kinesis_*, aws_msk_* or aws_mq_* resource exists, and no messaging SDK is in booking_lab/requirements.txt. The broker is the application's own database table, so durability, throughput and backlog visibility are coupled to the single PostgreSQL instance, and fan-out to another consumer needs new code. The 0.25s fixed poll is the only trigger; there is no backpressure signal and no dead-letter destination.
RECOMMENDATION
Keep the transactional outbox - it correctly couples state change to event and removing it reintroduces the dual-write problem. Change only the delivery target: publish to EventBridge or SQS instead of inserting into a second database, attach a dead-letter queue, and alarm on undelivered outbox depth.

INF-Q6: API Entry Point: stdlib HTTP server exposed directly with no gateway MEDIUM

Category: Infrastructure, Platform, and DevOps · Score 1 (Not Ready) · P2 · Effort Medium · Phase 2 · Evidence: booking_lab/service.py
FINDING
booking_lab/service.py::main() starts ThreadingHTTPServer(('0.0.0.0',8080), Handler) and booking_lab/run.py publishes it straight to a host port. No aws_api_gateway_*, aws_apigatewayv2_*, aws_appsync_*, aws_lb_* or CloudFront resource exists, and no reverse proxy is in the image. No throttling or rate limiting of any kind, no TLS termination, no edge request-size or connection-rate control (only an in-handler 8192-byte body cap and an 8s socket timeout), no WAF. ThreadingHTTPServer spawns an unbounded thread per connection, so connection-rate abuse translates directly into thread and database-connection exhaustion.
RECOMMENDATION
Place API Gateway (HTTP API) or an ALB in front of the service - ALB for TLS termination and health-checked target groups, API Gateway for per-client throttling and request validation. Terminate TLS at the edge, set a request-rate limit, and use /health/ready as the target-group health check. Retain the in-handler validation as defence in depth.

INF-Q7: Auto-Scaling: Fixed, imperatively-set capacity with no scaling policy MEDIUM

Category: Infrastructure, Platform, and DevOps · Score 1 (Not Ready) · P2 · Effort Low · Phase 2 · Evidence: booking_lab/run.py
FINDING
No auto-scaling exists. booking_lab/run.py starts exactly two API replicas and one worker with hard-coded --memory 256m --cpus 1 --pids-limit 128 (512m for the database). No aws_autoscaling_* or aws_appautoscaling_* resource, no scaling policy, no min/max capacity, no Lambda concurrency, and no database capacity scaling. Neither compute nor data capacity can respond to load. The two replicas exist to prove cross-replica correctness, not elasticity, and the single worker is fixed-throughput: its 0.25s loop with LIMIT 100 caps outbox drain and saga recovery regardless of backlog.
RECOMMENDATION
Once the ECS definition exists, attach Application Auto Scaling target tracking to the API service on ALB request-count-per-target rather than CPU - the workload is I/O-bound on the database and provider, so CPU is a poor load signal. Scale the worker on a custom metric from undelivered-outbox and pending-operation depth. Enable RDS storage autoscaling and size the connection ceiling against the task maximum, since db() opens a fresh connection per request.

INF-Q8: Backup and Recovery: Restore is tested but no backup policy is configured MEDIUM

Category: Infrastructure, Platform, and DevOps · Score 2 (Needs Work) · P2 · Effort Low · Phase 1 · Evidence: booking_lab/run.py
FINDING
Restore capability is genuinely tested: booking_lab/run.py::dump_restore() performs a real pg_dump, restores into a separate restore_check database, and asserts equal row counts and per-table MD5 row hashes for all six tables, recording hashes and the dump SHA-256 as evidence. Volume survival across restart is also proven. But there is no scheduled backup, no retention period, no PITR, no aws_backup_plan, no snapshot lifecycle and no cross-region copy. A restore procedure is verified; a backup policy does not exist. There is nothing to restore from after a volume loss, and no defined RPO or RTO. The dump is also written unencrypted to local disk.
RECOMMENDATION
On the managed database set backup_retention_period (7-35 days), enable PITR and KMS-encrypted automated snapshots, and add an AWS Backup plan with a cross-region copy rule for the audit data. Promote dump_restore() into the CI pipeline as a continuous fidelity check and record the resulting RPO/RTO.

APP-Q2: Monolith vs Microservices: One deployable unit and one shared schema holding three logical services MEDIUM

Category: Application Architecture · Score 2 (Needs Work) · P1 · Effort Medium · Phase 2 · Evidence: booking_lab/service.py
FINDING
booking_lab/service.py holds the booking API, the synthetic payment provider (Handler.payments) and the recovery/outbox worker, selected by sys.argv[1] from one image. All tables live in the single public schema of one database. Data isolation is nevertheless enforced and tested at the privilege layer: booking_lab/schema.sql revokes default public access and creates four roles with table- and column-level grants, and booking_lab/run.py::rights() proves payment_app cannot read bookings, booking_app cannot read audit_events or create tables, and no runtime role can UPDATE or DELETE audit rows. Cross-service communication is over HTTP, not shared tables, with no cross-module joins. Boundaries exist as privilege policy rather than deployable or schema boundaries: all services share one public schema in one database, and the payment provider - an external third party in any operated deployment - is in-process code in the same file as its caller. The three modes cannot be versioned, released, scaled or rolled back independently, and there is no package structure in the 302-line module.
RECOMMENDATION
Promote the existing role grants into per-service schemas (booking, payments, audit) so isolation is structural, and split booking_lab/service.py into packages along the lines the grants already describe. Extract the payment provider into its own repository, image and database - it is already an HTTP boundary with its own credential and table. Do NOT split the booking saga: operations, bookings and outbox must commit in one local transaction for the compensation and crash-recovery guarantees to hold.

APP-Q5: API Versioning Strategy: No API versioning and no published contract MEDIUM

Category: Application Architecture · Score 1 (Not Ready) · P2 · Effort Low · Phase 2 · Evidence: booking_lab/service.py
FINDING
Routes are unversioned literals plus one regex in Handler.dispatch: /bookings, /bookings/[a-f0-9]{64}, /health/live, /health/ready, plus /charge and /refund on the provider. No /v1/ segment, no Accept-Version or other version header, no version query parameter. The only version marker is the cosmetic server_version='BookingLab/1' header. No OpenAPI/Swagger/AsyncAPI/GraphQL specification and no changelog exists. Any change to request validation or response shape breaks every consumer simultaneously with no negotiation path or deprecation window. The risk is sharper here because the contract is exact - dispatch rejects any payload whose key set is not exactly {itinerary, amount} and whose itinerary does not match [A-Z]{3}-[A-Z]{3} - so even an additive field is breaking, and the Idempotency-Key fingerprint (SHA-256 over the canonicalised payload) means a shape change also invalidates replay equivalence for in-flight keys.
RECOMMENDATION
Introduce a version segment (/v1/bookings) before any external consumer exists, keeping current paths as aliases. Publish an OpenAPI document describing the request contract, every error code (400/401/402/403/404/405/409/503), the Idempotency-Key and X-Correlation-ID headers, and the replay semantics - all currently discoverable only by reading Handler.dispatch. Adopting an ASGI framework makes the specification generated rather than hand-maintained.

APP-Q6: Service Discovery: Endpoints supplied as environment variables with no dynamic discovery MEDIUM

Category: Application Architecture · Score 2 (Needs Work) · P2 · Effort Low · Phase 2 · Evidence: booking_lab/service.py
FINDING
booking_lab/service.py reads os.environ['PAYMENT_URL'] in payment() and DATABASE_URL/AUDIT_DATABASE_URL in db(). booking_lab/run.py::Lab.start materialises them into per-container .env files, resolving the provider as http://{prefix}-payments:8080 via Docker container-name DNS. No AWS Cloud Map/ECS Service Discovery, Consul, Istio or API catalog is used, and there is no client-side resolution, health-aware endpoint selection or retry-across-instances logic. The provider is a single fixed address: payment() has no instance-level failover, so if that endpoint is unreachable every charge attempt fails (correctly, into the retryable 503 path) until it is healthy. Endpoints are fixed at container start, so relocating a dependency requires a restart.
RECOMMENDATION
Keep configuration-driven endpoints - the right level of indirection for a service with one dependency - but resolve them through a discovery-backed name. On ECS, register the payment service in AWS Cloud Map and point PAYMENT_URL at the service-discovery DNS name; use the RDS endpoint name for DATABASE_URL. Add bounded retry with jitter in payment(), which the provider's advisory-lock-guarded idempotency already makes safe.

DATA-Q4: Stored Procedures and Schema Complexity: Test-only plpgsql trigger plus load-bearing PostgreSQL-specific concurrency constructs MEDIUM

Category: Data Platform Modernization · Score 2 (Needs Work) · P1 · Effort Medium · Phase 3 · Evidence: booking_lab/schema.sql
FINDING
Business logic is in the application layer, but the schema and concurrency design are coupled to PostgreSQL. booking_lab/schema.sql has one CREATE FUNCTION fail_booking_insert() LANGUAGE plpgsql and one BEFORE INSERT trigger, present solely so the test administrator can inject a real insert failure (there is deliberately no HTTP fault endpoint). Beyond those, the engine-specific constructs are load-bearing: session-scoped pg_advisory_lock held across local commits and the external payment call, pg_advisory_xact_lock(17,...) on a separate namespace in the provider, FOR UPDATE SKIP LOCKED, ON CONFLICT DO NOTHING, jsonb, clock_timestamp() and column-level GRANT SELECT(id). No business logic needs extraction - correctly, the saga is in Python - but the correctness model is portable only to PostgreSQL. Advisory locks make 'eight concurrent requests across two replicas produce exactly one charge' true and are the construct most at risk from infrastructure change: a transaction-level connection pooler silently breaks session-scoped advisory locks with no error. The plpgsql trigger also means production and test schemas differ unless it is excluded.
RECOMMENDATION
Keep PostgreSQL - this is not a reason to change engines. (1) Document the advisory-lock dependency as an explicit architectural constraint including its incompatibility with transaction-mode pooling, and make it a pre-cutover check for RDS Proxy or PgBouncer. (2) Move the fault-injection function and trigger into a schema.test.sql applied only by the harness so the deployed schema has no test artefacts. (3) Retain SKIP LOCKED and ON CONFLICT - both are supported across RDS/Aurora PostgreSQL.

SEC-Q4: Centralized Identity Integration: Application is its own token issuer with no external IdP MEDIUM

Category: Security Baseline · Score 1 (Not Ready) · P2 · Effort Medium · Phase 2 · Evidence: booking_lab/auth.py
FINDING
booking_lab/auth.py is both issuer (encode(), minting iss='booking-lab', aud='booking-api', 300s lifetime, default scope bookings:read bookings:write) and verifier (verify()), on one symmetric HMAC key supplied as JWT_KEY. booking_lab/run.py generates that key per run and mints tokens for the agent-a and agent-b principals. No aws_cognito_* resource, no OIDC discovery or JWKS endpoint, no SAML, no federation, no SSO. The module docstring states the symmetric JWT is confined to this local lab, so this is an acknowledged scope boundary. Because one symmetric key both signs and verifies, any component holding JWT_KEY - including the API itself - can mint a token for an arbitrary principal, so principal attribution in operations.principal and audit_events.principal is only as trustworthy as every key holder. There is no central place to revoke a principal, rotate signing material without a coordinated restart, enforce MFA, apply conditional access or audit token issuance. Scope assignment is a code default rather than IdP policy, and there are no refresh semantics.
RECOMMENDATION
Introduce a centralised IdP and reduce the application to a verifier only: Amazon Cognito user pools (or an existing enterprise OIDC provider) issuing asymmetrically-signed tokens, with the API validating against the published JWKS and mapping the scope/client_id claim to the existing checks. For the machine-to-machine callers agent-a/agent-b, use the OAuth2 client-credentials flow with per-client scopes so each caller has its own revocable identity. Keep auth.encode() as a test fixture only. Treat PAYMENT_TOKEN similarly - acceptable as a static bearer for a synthetic double, but rotated credentials or SigV4/mTLS for a real provider.

SEC-Q5: Secrets Management: No committed plaintext secrets, but env-var delivery with no store or rotation MEDIUM

Category: Security Baseline · Score 2 (Needs Work) · P1 · Effort Low · Phase 1 · Evidence: booking_lab/run.py
FINDING
There are no plaintext credentials committed anywhere: every secret is generated at runtime with secrets.token_hex in booking_lab/run.py::Lab.__init__ (32-byte JWT_KEY, 32-byte PAYMENT_TOKEN, 24-byte passwords for postgres and the four runtime roles), never hard-coded, and .gitignore excludes .env* and .local/. The harness avoids leakage: docker() truncates stderr and never prints container environments or bootstrap SQL, and Handler.log_message is a deliberate no-op so bearer tokens and request bodies are never logged. However secrets are delivered as plaintext environment variables through on-disk .env files (chmod 0600) consumed via docker run --env-file and read from os.environ. Because the harness generates fresh secrets per run, nothing exercises rotation, so no rotation path has been designed.
RECOMMENDATION

Enable managed RDS credential rotation and rotate PAYMENT_TOKEN; for JWT_KEY the asymmetric migration in SEC-Q4 removes the shared secret entirely and is the better fix. Keep runtime generation in run.py for tests, and keep the .gitignore entries, 0600/0700 permissions, stderr truncation and log_message suppression - all genuine strengths.

APP-Q4: Long-Running Process Handling: Bounded operations with durable async completion but no client status surface LOW

FINDING

SEC-Q3: API Authentication: Strict per-request JWT auth but no gateway throttling and symmetric keys LOW

Category: Security Baseline · Score 3 (Partial) · P2 · Effort Medium · Phase 2 · Evidence: booking_lab/auth.py
FINDING
Per-request token auth is enforced on every business endpoint and enforced carefully. Handler.dispatch extracts the Bearer value and calls auth.verify with required scope bookings:read for GET and bookings:write otherwise. auth.verify validates HMAC-SHA256 with hmac.compare_digest, rejects any header other than exactly {'alg':'HS256','typ':'JWT'} (closing algorithm confusion and alg:none), and checks iss, aud, exp, nbf, iat and a sub pattern before scope evaluation, returning 403 for insufficient scope versus 401 for invalid tokens. Token length is capped at 4096 bytes and the service refuses to start if JWT_KEY is under 32 characters. The provider independently requires its own bearer compared with compare_digest. run.py::auth() proves rejection of missing, expired, wrong-audience, wrong-issuer, not-yet-valid, wrong-key and insufficient-scope tokens with no charge created; isolation() proves cross-principal reads and cancels are denied. Score 4 requires intentionally public endpoints to sit behind a gateway with throttling and request validation. /health/live and /health/ready are unauthenticated and there is no gateway at all (INF-Q6=1), so there is no throttling, no per-client rate limit and no protection against token-guessing or request floods; /health/ready also opens a database connection on every unauthenticated call, a cheap amplification vector. Tokens are symmetric HS256 on one shared secret, so any holder of JWT_KEY can mint tokens for any principal, and verification is hand-rolled rather than library-backed.
RECOMMENDATION
Front the service with API Gateway or an ALB and apply a per-client throttle; keep /health/* reachable only from the load balancer's security group. Move to asymmetric signing (RS256/ES256) with a JWKS endpoint so the API holds only a public key, removing the shared-secret minting risk. Retain the existing claim-validation strictness and the 403-versus-401 distinction verbatim in whatever framework replaces the handler.
